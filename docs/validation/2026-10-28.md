# Sharing, privacy and update improvements

Scope: iPhone share sheet; expiring verification codes; per-device send/receive/image/code preferences; release notices and an AltStore/SideStore source; local-history encryption and group-key rotation on device removal. No new per-transfer receipt notifications were added.

## Behavior and compatibility

- Device preferences live on the device on which they are changed. A new clip carries its permitted recipients when a send restriction applies, so another current-version peer cannot accidentally relay it to an excluded device. Receiving also checks the original source's local policy. Live sending, incoming-image announcements and catch-up transfers respect these preferences. Already stored copies on other devices are not recalled when a preference changes.
- Restricted clips are sent only to peers advertising `policy1`. Earlier versions cannot safely enforce their recipient list. Updating the destination is required for iPhone's explicit share-to-device flow.
- Verification-code clips expire 180 seconds after their original timestamp, including pinned clips. Expiration propagates deletion tombstones; receiving, forwarding and catch-up independently reject expired codes. A code more than 60 seconds in the future is rejected rather than retained indefinitely. Copying a code from history remains a local code copy and never turns it into an ordinary unlimited-lifetime clip.
- On iOS, clipboard expiration uses the system's expiration date and disables Universal Clipboard propagation for that code. Mac and Windows clear the clipboard only if its change counter and text still match the original write. Android additionally checks Nearclip's item marker; if Android denies background clipboard access, Nearclip leaves the clipboard alone. The history and code-copy actions still expire. Apps must be running for app-managed clipboard cleanup; history expiration is enforced again on startup.
- Persistent history, images, large text side files and engine state use AES-256-GCM under an independent device-local key. The key uses Keychain on Apple platforms, Keystore wrapping on Android and DPAPI on Windows. CLI/test file-secret stores are for tests, not OS-protected storage. Legacy plaintext is atomically migrated. File names are authenticated to reject file substitution; decryption failures do not replace history with an empty file.
- Native preview and sharing APIs need readable image files. These are materialized in private temporary directories, removed on item deletion and on normal shutdown (Android clears its temporary directory at the next startup). This does not encrypt the operating system's clipboard, screenshots or arbitrary backups made before migration.
- Removing a device sends a fresh group key over established encrypted sessions to the remaining current-version peers. The removed device receives no new key. The old key is not retained as an offline recovery credential. Remaining devices that were offline, unreachable without the removed device, or running a version without `rekey1` must be paired again; the removal dialog discloses this before proceeding. Concurrent independent rotations are not automatically reconciled; re-pairing restores a split group.
- The iOS share extension receives one text, link or image, lists allowed destinations and owns a separate temporary engine. It never opens the main app's live store. Pairing context (without history) is passed through the common Keychain group. PNG/JPEG data is sent without a full decode; other formats are converted with a bounded thumbnail size. Keep the extension enabled when signing the IPA. Real personal-team/SideStore entitlement rewriting still needs installation acceptance.
- Sharing works on the LAN and can borrow the main app's remote proxy while that process is available. iOS does not allow the extension to keep the main app's Tailscale process alive indefinitely. If that proxy has stopped, open the main app for remote sending. A failed share does not claim that the destination copied it.
- Mac direct-download and Android settings check GitHub releases, at most once a day automatically, with an explicit retry. Store updates remain managed by their stores. No downloaded executable is launched automatically. The published source is generated from the IPA's real bundle version, build number, size, digest, entitlements and privacy declarations. Website deployment regenerates it on release publication/edit.
